# 1.39.0 plan: the Vault

> A design for keeping credentials, API keys, tokens and other secrets inside Pocket Code,
> encrypted, where agents can **use** them in commands without the values ever entering a
> model's context, a transcript, a memory index or a backup in plaintext. Written
> 2026-10-12 from Brad's direction; revised the same day after a three-critic council
> red-team ([findings](review/1.39.0-vault-redteam.md)). This is a plan, not a record of
> shipped behavior; the [workspace guide](../workspace-guide.md) describes what is live.

## Why

Agents in Pocket Code need credentials to do real work: an API key for Zoho, a token for
Stripe, a login for a vendor portal. Today the only way to hand one over is to paste it
into the conversation or leave it in a file on the box. Each of those leaks the value to
places it should never be:

| Where a pasted or echoed secret ends up today | Who can read it later |
|---|---|
| The request to the model provider | Anthropic or OpenAI, and their logs |
| The Claude Code transcript (`~/.claude/projects/**/*.jsonl`) and Codex rollout files | Anyone with the OS user's files; every later `--resume` of that session |
| Pocket's turn logs (`<data dir>/turnlogs/*.ndjson`) | Same |
| MemStem's index, when the value is in a typed message or the agent's prose | Every agent that searches memory, forever |
| The "away" summary and title digests Pocket sends to a helper model | The provider again, from a later turn |
| The nightly S3 backup of Pocket's data files | Anyone with the bucket |

The Vault closes those paths by making the only agent path one where **the model never
sees the value**: the agent names a secret, and Pocket's daemon runs the command with the
value in the child's environment, returning only scrubbed output. Agents cannot obtain a
value from the Vault at all in this release. The owner sees and copies values in the Vault
view, and sees every use.

Like Projects, Files and Tasks, the Vault must work for **any** install of the public
repo: no second service, no cloud KMS, no Google account. Brad's install is one deployment
of the generic feature.

## What it protects against, and what it does not

**Protects:**
- Secrets reaching the model provider. The value is never in a prompt, a tool result or
  the agent's environment.
- Secrets in transcripts, turn logs, Pocket's own search, MemStem and the helper-model
  digests. Nothing on the agent side ever holds the value, so there is nothing to scrub.
- Secrets at rest. The store is one encrypted file; a copied data directory or an S3
  backup holds ciphertext and nothing else, not even the list of what is stored. The key is
  never in the backup.
- Unnoticed use. Every run that used a secret is recorded with the session, the item, the
  command and the time, and the Vault view shows it.

**Does not protect:**
- Against the agent process as a whole. Agents run as the service's OS user, the same user
  that owns Pocket's files, as [SECURITY.md](../../SECURITY.md) says of the login
  password. The key lives in `.env`; an agent that goes looking can read it and the store.
  The Vault keeps secrets out of the places listed above and makes use visible; it is not
  process isolation. The passphrase mode planned for phase two protects a *locked* store
  against theft of the disk or a backup; it does not change what an unlocked daemon will do.
- Against misuse of a credential the agent is allowed to run with. A prompt-injected agent
  running an approved command with the Stripe key can do what that key allows. The
  defenses are the per-item policy, the approval of each new command and the record of
  use, not secrecy.
- Against secrets pasted into a terminal or code-server session outside Pocket. The skill,
  written into the user's skill folders, is the only guard there.
- Against the command itself. The daemon runs the child; if the child writes the value
  somewhere or sends it off the box, output scrubbing does not see that. Policy and
  approval decide which commands run; scrubbing only reduces accidental exposure.

## The model

A vault **item** is one credential:

| Field | Notes |
|---|---|
| `id` | short random id, like tasks |
| `name` | unique slug the agent refers to: `zoho-books`, `stripe-live`. 1–64 chars, `[a-z0-9-]`. Renaming keeps the id; a removed name cannot be reused for 30 days |
| `kind` | `api_key`, `token`, `login`, `note` |
| fields | `api_key` and `token`: `value`. `login`: `username`, `password`. `note`: `text` |
| `url`, `notes`, `tags` | owner's annotations, encrypted with everything else; `show` returns `url` and `tags` to agents, never `notes` |
| `policy` | `ask` (default), `auto`, `owner` — see Access |
| `recipes` | commands the owner has approved for this item (see Access) |
| `expiresAt` | optional; the Vault view shows expiring items |
| `revision`, `createdAt`, `updatedAt`, `lastUsedAt`, `lastUsedBy` | |

The whole store (items, recipes, settings) is **one encrypted file**, `<data dir>/vault.enc`:
a version byte, a fresh 12-byte IV per write, the GCM tag, and the ciphertext of the JSON.
There is no plaintext metadata on disk. The daemon decrypts it into memory at boot, holds
a write mutex, checks item revisions on update, and writes atomically. A tag mismatch or a
malformed file fails closed: the Vault reports "cannot be opened" and serves nothing.

## Access

### Agents: run a command with the secret in its environment

```bash
pocket-vault run --env ZOHO_TOKEN=zoho-books -- node sync-invoices.mjs
pocket-vault run --env USER=vendor-portal.username --env PASS=vendor-portal.password -- python3 fetch.py
```

`run` sends the daemon the command, arguments, working directory and the variable-to-item
bindings over the loopback route. **The daemon** decrypts the values, spawns the child
itself with those variables added to a filtered environment, no TTY, `stdio` piped, and
streams stdout and stderr back to the CLI through a scrubber that replaces each value, and
its base64 and URL-encoded forms, with `{{vault:name}}` using a sliding window across
chunks. The CLI prints what comes back and exits with the child's status. Output is capped
(1 MB, then truncated with a note); the child is killed at a timeout (default 10 minutes,
`--timeout`).

Values never pass to the CLI, never appear in arguments, and are not in the agent's
environment. Multi-field items need the field named (`name.field`); `api_key` and `token`
default to `value`.

What decides whether a run happens:

- **`auto`** policy: any command runs, and is recorded.
- **`ask`** policy (the default): the command runs if it matches one of the item's
  **recipes**. Otherwise the daemon files a **request** (item, command, cwd, session), sends
  a push ("Zoho Books: allow `node sync-invoices.mjs`?"), and the CLI waits. The owner
  answers in the Vault view or from the push: *Allow once*, *Always allow this command*
  (which saves a recipe: the exact binary and arguments, with the cwd), or *Deny*. The CLI
  waits up to 90 seconds, then prints `pending <request id>` and exits 4; the agent runs
  `pocket-vault wait <request id>` to continue, and the instruction line says so. A request
  expires after 15 minutes. A recipe is exact: a changed argument is a new request.
- **`owner`** policy: agents cannot use the item. `run` fails with a message to ask the
  owner.

Under Review actions the owner also approves the `pocket-vault run …` Bash call itself,
which shows the item name and the command. Under Full access there is no native approval,
which is why `ask` is the default: the Vault's own request is the gate.

Because the daemon runs the child, the child runs with the daemon's permissions, outside
any sandbox the agent's CLI applies. Under Codex's Review mode the read-only sandbox blocks
loopback, so `pocket-vault run` fails there until the owner escalates the turn; phase one
documents that rather than working around it. (Whether Codex's network approval can allow
loopback alone is to be tested, not assumed.)

### Agents: store a secret they meet

```bash
pocket-vault put stripe-live --kind api_key --from-env STRIPE_SECRET_KEY
pocket-vault put vendor-portal --kind login --from-file /tmp/creds.json --map username=user,password=pass
printf '%s' "$VALUE" | pocket-vault put twilio-auth --kind token --stdin
```

`put` by an agent is **create-only**: an existing name is refused, so an injected agent
cannot replace `stripe-live`. The value travels in the request body over loopback, never
as an argument. New items get policy `ask` and no recipes. `put` prints the name only. A
secret the agent met in a file or a tool result has already reached the provider; `put`
protects every later turn, not that one, and the skill says to tell the owner it was seen.

### The owner: the Vault view

Add, edit, view and copy items; set policy; manage recipes; answer requests; read the
history. A value is shown only on tap, fetched one at a time by `POST
/api/vault/:id/field` (POST, no caching, cookie only), and every owner view is recorded.

### Who may do what

Enforced in the daemon on every route, and tested over raw HTTP with each credential:

| Action | Owner (cookie) | Agent (loopback CLI token) |
|---|---|---|
| list names, kinds, urls, tags, policy, last used | yes | yes |
| read a value | yes, one field at a time, recorded | **no route** |
| run a command with values | yes | yes, by policy and recipes |
| create an item | yes | yes, create-only |
| change a value, url, notes, tags, expiry | yes | no |
| change policy or recipes | yes | no |
| answer a request | yes | no |
| remove, restore | yes | no |
| read the audit log | yes | own session's rows only |
| rotate the key, lock, unlock | yes | no |

The CLI token stays the shared loopback bearer the other libraries use. **Session
attribution** no longer rests on a caller-supplied id: each runner (the Claude runner and
each Codex app-server) is spawned with `POCKET_SESSION_ID` and a per-runner
`POCKET_RUNNER_TOKEN` in its environment; the CLI sends both, and the daemon maps the
runner token to the live runner and its current turn. A call without a runner token is a
terminal or code-server call: allowed, recorded as `terminal`, and its requests are pushed
like any other.

## Entry points: how secrets get in

1. **The Vault view.** The normal way. Add item, pick a kind, paste the value.
2. **The composer's "Store in the Vault" control.** A button beside Attach that opens the
   add sheet without the text ever entering the message. The sheet's value field is not
   mirrored into the draft, local storage, the outbox or the recent-prompts list. Automatic
   detection of secret-shaped pastes is phase two (see below); in phase one the control is
   there and the skill reminds the owner.
3. **The agent, on first sight**, with `put` as above.

## The agent's interface

**CLI** `scripts/pocket-vault.mjs`, bin `pocket-vault`, loopback CLI token plus the runner
token from the environment, exit 3 when the Vault is off, exit 4 when a request is pending:

| Command | Returns |
|---|---|
| `list [--kind k] [--tag t]` | names, kinds, urls, tags, policy, expiry, last used; **never values or notes** |
| `show <name>` | one item's metadata, which fields exist, and its recipes; never values |
| `run [--env VAR=name[.field]]… [--cwd dir] [--timeout s] -- <cmd…>` | the child's scrubbed output and exit status, or `pending <id>` |
| `wait <request id>` | waits for the owner's answer, then runs or reports denial |
| `put <name> --kind k (--from-env VAR \| --from-file path [--map f=key,…] \| --stdin) [--url u] [--tags t]` | the name; create-only |
| `history [--name n]` | this session's audit rows |

**Per-turn instruction line**, appended like the projects, files and tasks lines when the
Vault is on: the Vault exists; secrets are referred to by name and used with
`pocket-vault run`; never print, echo, write to a file, or put in a message any secret
value; store any secret encountered with `put` at once, tell the owner it was seen, and
use the name after that; if a run comes back `pending`, say so and use `wait`; if a run is
refused, say so and stop, do not look for another way; a `{{vault:name}}` placeholder in a
message is the owner handing over a stored secret by name.

Because Claude's `--append-system-prompt` is fixed when the runner is spawned and Codex
receives developer instructions on thread start, turning the Vault on **restarts idle
runners** and marks running sessions "rules apply from the next turn". When Codex's
`config.toml` sets `developer_instructions`, Pocket's line is not delivered; Settings shows
a warning in that case.

**Skill** `skills/pocket-vault/SKILL.md`, installed into the Claude Code and Codex skill
folders while the feature is on (fourth entry in `skills.mjs`), with the procedure, the
kinds, the policy meanings, `run` examples for common tools (node, python, curl with a
header from an environment variable, gws, ssh with a key file written by the child itself),
and the rules above.

## Encryption and the key

- **AES-256-GCM over the whole store** with Node's `crypto`, no new dependency. One key,
  one blob, a fresh random IV per write, the version byte as associated data, tag checked
  before anything is parsed.
- **The key** is `POCKET_VAULT_KEY` in `.env`: 32 random bytes, base64. Settings → Vault
  explains how to generate it (`openssl rand -base64 32`) and shows "set `POCKET_VAULT_KEY`
  to turn the Vault on". The daemon reads it at boot into a module variable and **deletes
  it from `process.env`**, so no child of the daemon can inherit it, whatever spawn path
  it takes. (The red-team found spawns that bypass `agentEnv()`: the voice engine,
  thumbnail workers, `git` in agent repos, the keepers, two `execSync` calls. Those get a
  single `childEnv()` wrapper in this release, with a test that greps for bare `spawn(` and
  `execFile(` calls, but the key does not rely on it.)
- **Rotation** is an owner action in Settings: the daemon rewraps the store under a new key,
  keeps both keys in memory until restart, and shows the new key **once in the UI** for the
  operator to put in `.env`. Nothing prints a key to a terminal or a transcript. Backups
  taken before rotation need the old key; the operations guide says to keep the retired
  key with the backup it matches.
- **Backups.** A generic install backs up `vault.enc` and `vault-audit.jsonl` with the
  other data files and keeps the key elsewhere. Brad's backup script uses an allowlist and
  must add both files. A restore without the key yields nothing, which is the intended
  outcome.
- **Passphrase mode** (phase two): the key is derived from a passphrase with scrypt and
  held only in memory; the store is unusable after a restart until the owner unlocks it.
  This protects a locked store against theft of the disk or a backup. It does not change
  what an unlocked daemon does, and the plan says so.

## Server

- Setting `vault` (off by default; on requires `POCKET_VAULT_KEY`), beside `projects`,
  `documents`, `tasks`; `features.vault` on `/api/me`; the skill is installed and removed
  with it; idle runners restart on toggle.
- Routes behind `requireBoardAuth` for the agent-allowed actions and `requireAuth` (cookie)
  for the rest, per the matrix; `vaultOn` 404 `vault_off`. All Vault responses are
  `Cache-Control: no-store`, excluded from the service worker, and mutations check the
  `Origin` header against the app origin. Notes, reasons and command text are rendered as
  text, never HTML.
- **Audit log** `<data dir>/vault-audit.jsonl`, mode `0600`, append with fsync like
  `approval-decisions.jsonl`: time, item id and name, action (`run`, `run-denied`,
  `request`, `request-answered`, `owner-view`, `put`, `update`, `remove`, `restore`,
  `rotate`), session id and turn id from the runner token (or `terminal`), the command and
  cwd for runs, the request outcome. Never a value, never a hash of a value. Reasons and
  command text are clipped and stored as text. If the audit write fails, the action fails:
  no unrecorded release. The log records that a value was released to a command; what the
  command then did with it is outside the record.
- **Requests** `<data dir>/vault-requests.json`: id, item id and revision, command, cwd,
  session, created, expires, answer. Single use; answered atomically; invalid if the item
  changed meanwhile; expired after 15 minutes. A push per request (`vault` kind, url
  `#/vault/requests`). The approval-inbox mechanism is not involved: it relays native
  permission requests to the model process and cannot host a Pocket-originated row.
- **Runs** are spawned by the daemon with `childEnv()` plus the bound variables, `cwd`
  from the request (must be an existing directory the OS user can read), `detached:false`,
  killed on timeout or when the CLI disconnects. Concurrency is capped (8 at a time).

## MemStem

With no agent path to a plaintext value, there is nothing for MemStem to redact in this
release; the adapters already reduce tool calls and results to markers, and the daemon's
own search and digests read transcript text that never held a value. What remains is the
prose case: the owner types a secret, or an agent met one in a file and repeats it. For
that, MemStem's planned ingest scrub is the backstop and is tracked in the MemStem repo.
The placeholder grammar to share is `{{vault:[instance/]name}}`; MemStem's current doc
writes `{{vault:slug/key}}` and should be updated to this form when that work starts.

## Phases

**Phase one, 1.39.0:**
- `vault.mjs`: whole-store AES-256-GCM, in-memory store with a write mutex and revisions,
  atomic writes, trash with the 30-day purge, requests, recipes, audit; key read from
  `.env` and removed from `process.env`; `childEnv()` for every spawn.
- Routes and the authorization matrix, tested over raw HTTP with both credentials; runner
  tokens and `POCKET_SESSION_ID` in runner environments (Claude runner, Codex app-server).
- `pocket-vault` CLI: `list`, `show`, `run`, `wait`, `put`, `history`.
- Daemon-side runs with env injection, piped stdio, the streaming scrubber, caps and
  timeouts.
- Vault view: list, item sheet (show and copy per field, policy, recipes, history), editor,
  requests list, remove and restore; composer "Store in the Vault" control; Settings →
  Vault with the key instructions, rotate, and the Codex override warning.
- Skill, per-turn instruction line, runner restart on toggle.
- Tests: crypto round trip, tamper and wrong-key fail closed, rotation; concurrency and
  crash recovery of the store; 404 while off; the matrix over raw HTTP including the
  tunnel refusal; values never in any agent-reachable response; `run` injection by env, a
  child's `echo "$SECRET"` scrubbed including split chunks and base64 and URL-encoded
  forms, no value in any fixture transcript; policy and recipe matrix; request lifecycle
  (once, always, deny, expire, item changed); `put` create-only; audit rows carry no values
  and the action fails when the log cannot be written; no bare `spawn(`/`execFile(`;
  the key absent from every child's environment; agent line; skill install. Browser suite
  for the view, the requests flow and the composer control; phone 390 plus axe.

**Phase two:**
- **Reveal with approval**, if a real need remains after "typed by Pocket" below: an
  explicit per-item allowance, a request like a run request, and a parse-aware scrubber
  that walks JSON string values in the turn's new transcript lines and the turn log as
  they arrive, with a separate Codex pass. Labeled as a disclosure with a rotation prompt,
  and never claimed to reach the provider's logs or MemStem distillations already made.
- **Typed by Pocket**: form fills for the Playwright tool where the agent passes a
  placeholder and Pocket's side substitutes the value, so logins stop needing a reveal.
  Depends on where the browser runs; not designed yet.
- Passphrase unlock and auto-lock.
- Composer detection of secret-shaped pastes: `preventDefault`, hold the text in memory
  until the chip is answered, run on `input` too, skip the recent list and title call for a
  flagged message.
- Cards, if ever: virtual card per merchant, never CVC at rest, filled by Pocket's side.
- TOTP seeds with code generation; expiry reminders through Tasks.
- An ultra-vault backend for tenant boxes. Its `kind` is an enforced enum and `notes` is
  capped, so this needs a value envelope and a sidecar, or ultra-vault changes first.
- MemStem ingest scrub against the shared placeholder grammar.

## Non-goals

- A general password manager for people. No browser extension, no autofill on other
  devices, no sharing between users. 1Password and the like do that; the Vault is for what
  agents on this box need.
- Process isolation from the agent, or protection against the command the owner approved.
- A guarantee that a secret typed into a conversation is caught. Storing it first is the
  control; MemStem's scrub is a backstop.
- Sharing items across Pocket instances. Each install has its own store.
