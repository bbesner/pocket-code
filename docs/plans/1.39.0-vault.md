# 1.39.0 plan: the Vault

> A design for keeping credentials, API keys, tokens, card numbers and other secrets inside
> Pocket Code, encrypted, where agents can **use** them without the values ever entering a
> model's context, a transcript, a memory index or a backup in plaintext. Written
> 2026-10-12 from Brad's direction. This is a plan, not a record of shipped behavior; the
> [workspace guide](../workspace-guide.md) describes what is live.

## Why

Agents in Pocket Code need credentials to do real work: an API key for Zoho, a login for a
vendor portal, a card for a purchase. Today the only way to hand one over is to paste it
into the conversation or leave it in a file on the box. Each of those leaks the value to
places it should never be:

| Where a pasted or echoed secret ends up today | Who can read it later |
|---|---|
| The request to the model provider | Anthropic or OpenAI, and their logs |
| The Claude Code transcript (`~/.claude/projects/**/*.jsonl`) and Codex rollout files | Anyone with the OS user's files; every later `--resume` of that session |
| Pocket's turn logs (`<data dir>/turnlogs/*.ndjson`) | Same |
| MemStem's index, when the value is in a typed message or the agent's prose | Every agent that searches memory, forever |
| The "away" summary and title digests Pocket sends to a helper model | The provider again, from a later turn |
| The nightly S3 backup of Pocket's data files | Anyone with the bucket |

The Vault closes those paths by making the ordinary case one where **the model never sees
the value at all**. The agent asks for a secret by name and Pocket injects it out of band.
Seeing a value is the exception, is a per-item policy, is audited, and can require a tap on
the owner's phone.

Like Projects, Files and Tasks, the Vault must work for **any** install of the public
repo: no second service, no cloud KMS, no Google account. Brad's install is one deployment
of the generic feature. Tenant installs that already run `ultra-vault` beside Pocket use it
as a backend instead of the built-in store.

## What it protects against, and what it does not

**Protects:**
- Secrets reaching the model provider. In *use* mode the value is never in a prompt.
- Secrets in transcripts, turn logs, Pocket's own search, MemStem, and the helper-model
  digests. *Use* mode never writes the value there; *reveal* mode scrubs it afterwards.
- Secrets at rest. The store is encrypted; a copied data directory or an S3 backup holds
  ciphertext only. The key is never in the backup.
- Silent use. Every use and reveal is logged with the session, item, time and reason, and
  the Vault view shows "last used by …".

**Does not protect:**
- Against the agent process itself. Agents run as the service's OS user, the same user that
  owns Pocket's files, as [SECURITY.md](../../SECURITY.md) says of the login password.
  With the key in `.env` (phase one) a determined or prompt-injected agent could read the
  key and the store. The passphrase mode (phase two) removes the key from disk, so the
  agent would have to ask Pocket, and Pocket would ask the owner. The Vault turns "could
  silently" into "would have to ask, visibly". It is not process isolation.
- Against a *reveal* the owner approves. Once a value is in the model's context it has gone
  to the provider. Scrubbing cleans the local copies; it cannot reach a vendor's logs.
- Against secrets pasted into a terminal or code-server session outside Pocket. The
  composer detection and the per-turn instructions cover Pocket turns; the skill, written
  into the user's skill folders, is the only guard for other sessions.

## The model

A vault **item** is one credential. Fields:

| Field | Notes |
|---|---|
| `id` | short random id, like tasks |
| `name` | unique slug the agent refers to: `zoho-books`, `stripe-live`, `amex-brad`. 1–64 chars, `[a-z0-9-]` |
| `kind` | `api_key`, `token`, `login`, `card`, `note` |
| fields | by kind, see below; every field value is encrypted |
| `url` | where it is used (plain, searchable) |
| `notes` | plain text, searchable, **must not contain the secret**; the UI warns on a secret-shaped paste |
| `tags` | plain |
| `policy` | `use` (inject only, no reveal), `reveal` (agent may read it after the owner approves), `reveal-auto` (agent may read it without asking; for low-value items), `locked` (UI only; agents cannot use or reveal) |
| `expiresAt` | optional; the Vault view shows expiring items and a Task can be offered |
| `createdAt`, `updatedAt`, `lastUsedAt`, `lastUsedBy` | session id and kind of access |

Fields by kind: `api_key` and `token` hold `value`; `login` holds `username`, `password`,
and optionally `totp` (phase two); `card` holds `number`, `expiry`, `cvc`, `cardholder`,
`billingZip`; `note` holds `text`. Usernames, card last-four and expiry month are stored
encrypted like everything else but may be shown in lists, since they identify the item
without compromising it.

Items live in `<data dir>/vault.json`, written atomically by the server alone, like the
other libraries. The file holds metadata in the clear and every secret field as
ciphertext, so the existing nightly backup can include it as is. The key never lives in
that file or in the backup.

## Access modes

### Use (the default): the agent never sees the value

The agent runs a command with the secret injected by Pocket:

```bash
pocket-vault run --env ZOHO_TOKEN=zoho-books -- node sync-invoices.mjs
pocket-vault run --env STRIPE_SECRET_KEY=stripe-live --env STRIPE_WEBHOOK_SECRET=stripe-webhook -- npm run reconcile
```

`run` asks the daemon for the named items, puts their values into the **environment** of
the child process (never into its arguments, so they are not in `ps`, the shell history or
the approval card), runs it, and **scrubs** every injected value from the child's stdout
and stderr before they return to the agent, replacing it with `{{vault:name}}`. The agent
sees that the command ran and what it printed, minus the secret.

Two conveniences on the same mechanism:

- `--header "Authorization: Bearer {{zoho-books}}"` for a `curl`-shaped command: Pocket
  resolves the placeholder into an environment variable and rewrites the argument to
  `"$POCKET_VAULT_1"` form, so the value is still never on the command line.
- `--file .env.local KEY=item …` writes a temporary file with mode `0600` for tools that
  only read a file, and removes it when the command exits. The agent is told the path, not
  the contents; the skill forbids reading it back.

`run` works under Review actions the same way any other Bash command does: the owner sees
`pocket-vault run --env ZOHO_TOKEN=zoho-books -- node sync-invoices.mjs` on the approval
card, which names the item but not the value. Under Codex's read-only sandbox the command
needs the same approval a network-using command would.

### Reveal: the value enters the model's context, on purpose

Some work needs the plaintext in the model's hands: Playwright typing a password into a
login form, a card number into a checkout page, a code read off a screenshot. For those:

```bash
pocket-vault reveal vendor-portal --reason "Log in to the ABC vendor portal to download the September invoice"
```

- If the item's policy is `use` or `locked`, the command refuses and tells the agent to
  ask the owner to change the policy in the Vault view. The agent should then say so and
  stop; it must not try other routes.
- If the policy is `reveal`, the daemon posts an **approval card** in the conversation,
  the same surface as native action approvals: item name, kind, the agent's reason, the
  session. The command blocks until the owner taps Allow or Deny (or a 10-minute timeout
  denies). Push notification like any approval.
- If the policy is `reveal-auto`, the value is returned at once and the reveal is logged.
- The value is printed once. The daemon records a **reveal** for that session, which
  arms the end-of-turn scrub (below).

A reveal in a session under Full access still asks, because the card is Pocket's, not the
CLI's permission system.

### In the Vault view

The owner opens an item, taps the masked field to show it, taps Copy. Reveals from the UI
are logged too (`by: owner`), with no session. The UI never puts values in a list response;
`GET /api/vault` returns metadata only, and a field value is fetched one at a time with
`GET /api/vault/:id/field/:name`.

## Entry points: how secrets get in

1. **The Vault view.** Add item, pick a kind, fill the fields. Paste works as normal here.
2. **The composer.** When the owner pastes text that looks like a secret into the message
   composer, Pocket offers a chip above the composer: *"That looks like an API key. Store
   it in the Vault as … and send the message with a placeholder?"* Accepting opens a tiny
   sheet (name, kind guessed, policy defaults to `use`), stores the item, and replaces the
   pasted text in the draft with `{{vault:name}}` **before the message is sent**. This is
   the only point in the system that can stop a secret reaching the provider, so it is in
   the browser, not in the daemon. Declining sends the text as pasted; nothing is logged.
   Detection is a small regex pack (AWS `AKIA…`, GitHub `ghp_`/`github_pat_`, OpenAI
   `sk-…`, Anthropic `sk-ant-…`, Slack `xox…`, Stripe `sk_live_`, Google `AIza…`, JWTs,
   PEM private keys, Luhn-valid 13–19 digit card numbers) plus a high-entropy check on
   long single tokens. False negatives are accepted; the owner can always use the view.
3. **The agent, on first sight.** When an agent meets a secret in a file, a tool result or
   a message, the skill tells it to store the value at once and refer to it by name from
   then on:
   ```bash
   pocket-vault put stripe-live --kind api_key --from-env STRIPE_SECRET_KEY   # value from the agent's environment
   pocket-vault put vendor-portal --kind login --from-file /tmp/creds.json     # value from a file; file is left alone
   printf '%s' "$VALUE" | pocket-vault put twilio-auth --kind token --stdin
   ```
   The value never passes as an argument. `put` prints the item name and nothing else.
4. **Import.** `pocket-vault import --from ultra-vault` for tenant boxes moving to the
   built-in store, and a JSON import for migrating from another manager, with the file
   shredded afterwards on request. Not in phase one.

## The agent's interface

**CLI** `scripts/pocket-vault.mjs`, bin `pocket-vault`, loopback CLI token like the other
libraries, exit 3 when the Vault is off:

| Command | Returns |
|---|---|
| `list [--kind k] [--tag t]` | names, kinds, urls, tags, policy, last used; **never values** |
| `show <name>` | one item's metadata and which fields exist; never values |
| `run [--env VAR=name]… [--header …]… [--file path VAR=name…] -- <cmd…>` | runs the command with values injected; output scrubbed |
| `reveal <name> [--field f] --reason "…"` | the value, after policy and approval |
| `put <name> --kind k (--from-env VAR \| --from-file path \| --stdin) [--field f] [--url u] [--notes n] [--tags t]` | stores; name only |
| `update <name> …` | metadata only; values change through `put --field` |
| `remove <name>` | refuses unless policy allows removal by agents; off by default |

**Per-turn instruction line**, appended like the projects, files and tasks lines when the
Vault is on: the Vault exists; secrets are referred to by name and used with
`pocket-vault run`; never print, echo, write to a file, or put in a message any secret
value; store any secret encountered with `put` at once and use the name after that;
`reveal` only when the work truly needs the plaintext, with a reason, and never for
convenience; if a placeholder `{{vault:name}}` appears in a message, that is the owner
handing over a stored secret by name.

**Skill** `skills/pocket-vault/SKILL.md`, installed into the Claude Code and Codex skill
folders while the feature is on, with the full procedure, the kinds, the policy meanings,
examples of `run` for common tools (curl, node, python, gws, ssh with a key file), and the
rules above.

## Encryption and the key

- Each secret field is encrypted with **AES-256-GCM** under a per-item data key; the data
  key is wrapped with the master key. Rotating the master key rewraps data keys without
  touching the ciphertext; replacing a value re-encrypts one field. Node's `crypto` only,
  no new dependency.
- Ciphertext records carry a version byte, the IV, the tag and the item id as associated
  data, so a value cannot be moved between items.
- **Master key sources**, in order of preference at boot:
  1. **Passphrase** (phase two): the store holds a salt and a verifier; the owner unlocks
     the Vault in Settings or at first use, the key is derived with scrypt and held only in
     daemon memory. Auto-lock after a configurable idle period and on restart. While
     locked, `run` and `reveal` fail with "the Vault is locked; ask the owner to unlock
     it" and the owner gets a push. Nothing on disk can decrypt the store.
  2. **`POCKET_VAULT_KEY`** in `.env` (phase one): a 32-byte base64 key, generated by
     `pocket-vault init`. Same model as `ultra-vault`. Simple, survives restarts
     unattended, and the agent could read it. Documented as such.
  The two can be combined: the env key wraps the store so unattended reminders and
  `use`-mode runs work, and `reveal` additionally requires the passphrase. Decide in
  phase two.
- `POCKET_VAULT_KEY` joins `POCKET_PASSWORD`, `POCKET_SECRET` and `VAPID_PRIVATE` in the
  list that `agentEnv()` strips from every agent, hook and helper process.
- The backup script keeps backing up `vault.json`; it must never pick up `.env`, which
  it already excludes. A restore without the key yields metadata and no values, which is
  the intended outcome.
- `pocket-vault rotate-key` rewraps under a new key and prints the new value for `.env`.

## Server

- Setting `vault` (off by default) beside `projects`, `documents`, `tasks`; `features.vault`
  on `/api/me`; the skill is installed and removed with it.
- Routes behind `requireBoardAuth` (cookie, or the loopback CLI token with the same
  tunnel-refusal rule), `vaultOn` 404 `vault_off`:
  `GET /api/vault` (metadata), `POST /api/vault` (add), `PATCH /api/vault/:id`,
  `DELETE /api/vault/:id`, `GET /api/vault/:id/field/:name` (one value, logged),
  `POST /api/vault/use` (CLI `run`: returns values for the session, logged as `use`),
  `POST /api/vault/reveal` (CLI `reveal`: policy, approval card, logged),
  `GET /api/vault/audit`, `POST /api/vault/lock`, `POST /api/vault/unlock`.
- The CLI token is accepted on `/api/vault*` as on the other library routes. It is the
  same token, so an agent that can file a task can call `use`; policy is enforced in the
  daemon, and the audit log is the record. (A separate vault token would not change the
  threat model: both files are readable by the OS user.)
- **Audit log** `<data dir>/vault-audit.jsonl`, mode `0600`, append-only with fsync like
  `approval-decisions.jsonl`: time, item id and name, access (`use`, `reveal`,
  `reveal-auto`, `owner-view`, `put`, `update`, `remove`, `denied`, `locked`), session id,
  turn id, reason, approval outcome. Never a value, never a hash of a value.
- **Reveal approvals** reuse the approval inbox mechanism: the card is a Pocket-originated
  request with kind `vault-reveal`, rendered like a native approval, answered from any
  device, and resolved back to the blocked CLI call over the loopback route.
- **End-of-turn scrub.** When a session has a reveal on record, the end-of-turn pass that
  already restamps the transcript also replaces each revealed value, wherever it occurs in
  the turn's new bytes, with a same-length placeholder (`{{vault:name}}` padded with
  spaces, or truncated to the value's length), so the byte-preserving restamp machinery
  applies unchanged. The same pass runs over the turn log. The scrub is best effort:
  values split across chunks or transformed (base64, URL-encoded) are not caught, and
  the transcript may have already been read by a `--resume` from a terminal. A reveal is
  flagged in the Vault view as "revealed in session … on …" so the owner knows the item
  may deserve rotation.
- **Digests and search.** The away-summary and task-briefing digests and Pocket's fallback
  search read transcript text, so they run after the scrub, and the digest builder also
  drops any line containing a currently revealed value as a belt-and-braces check.

## MemStem

MemStem's `docs/secrets.md` describes the matching half: `{{vault:name}}` placeholders in
memories, a regex scrub on ingest, an audit table, and a `SecretBackend` interface with
`UltraVaultBackend` as the default. None of it is built; the 2026-08-31 review concluded
MemStem should integrate with an existing vault rather than build one. The Pocket Vault is
that vault for Brad's boxes, and `ultra-vault` stays the backend for tenants. Pocket's part
of the contract:

- The placeholder syntax is `{{vault:<name>}}`, identical on both sides.
- `GET /api/vault/placeholders` (loopback token) returns the current names so MemStem's
  scrub can validate a placeholder it finds, and `POST /api/vault/use` lets a MemStem
  resolve call fetch a value under the same policy and audit as an agent.
- MemStem's Claude Code and Codex adapters already index tool calls and results as
  `[tool_use: name]` / `[tool_result]` markers, not their content, so `use`-mode runs and
  `put` calls leave nothing to scrub. Typed messages and the agent's prose are what MemStem
  indexes, and those are what the composer detection and the skill's rules protect.

The MemStem work (ingest scrub, audit, resolve) is tracked in the MemStem repo, not here.

## Backends

`vault.mjs` exposes one interface: `list`, `get(id)`, `values(id, fields)`, `put`, `update`,
`remove`, `lock/unlock`. Two implementations:

- **Built-in** (default): `vault.json` plus the key source above.
- **ultra-vault** (`POCKET_VAULT_BACKEND=ultra-vault`, `ULTRA_VAULT_URL`,
  `ULTRA_VAULT_API_KEY`): maps items to its `/secrets` API, with kind and policy carried
  in its `notes` field as JSON until ultra-vault grows the columns. Phase two, so the
  Ramesh and Siri boxes get the same agent interface without a second store. The API key
  is stripped from agent environments like the built-in key.

## UI

Follows the library pattern (rail segment, `#/vault` view as tab, split pane or window,
phone chip, Settings → "Projects, files, tasks & vault"). Built under `design-studio` with
the `impeccable` scan, pinned to the existing warm-charcoal identity; nothing new in the
palette. Elements:

- **List**: name, kind icon, url host, tags, policy badge, last used, expiring soon.
  Search over names, urls, notes and tags. Kind and tag filters.
- **Item sheet**: masked fields with Show and Copy per field; policy picker with one line
  of plain-language consequence per choice ("Agents can use this in commands but never
  see it", "Agents can read it after you approve", "Agents can read it without asking",
  "Only you"); notes; url; tags; expiry; a **History** section listing the audit rows for
  the item; Remove (to a trash with the usual 30-day purge, values kept encrypted until
  purge).
- **Editor**: kind-specific fields; the secret field warns if the value looks like a
  placeholder or is empty; the notes field warns on a secret-shaped paste.
- **Composer chip**: the "Store in the Vault?" offer on a detected paste; one tap to
  accept, one to dismiss; never blocks sending.
- **Reveal card**: in the conversation, the same shape as an action approval, with the
  item name, kind, reason and session, and Allow / Deny.
- **Lock state** (phase two): a lock glyph on the rail segment; unlock sheet with the
  passphrase; "Lock now" in Settings; idle-lock setting.

## Phases

**Phase one, 1.39.0:**
- `vault.mjs` store with AES-256-GCM, per-item keys, `POCKET_VAULT_KEY`, atomic writes,
  trash, audit log; `agentEnv()` strips the key.
- Routes, setting, `/api/me` feature, skill sync, per-turn instruction line for Claude and
  Codex.
- `pocket-vault` CLI: `init`, `list`, `show`, `put`, `update`, `run` with `--env` and
  output scrubbing, `reveal` with `reveal-auto` and `reveal` (approval card), `remove`.
- Composer paste detection and the placeholder substitution.
- Vault view: list, item sheet, editor, policy, history, remove/restore.
- End-of-turn scrub for reveals.
- Tests: store rules and crypto round-trips, key rotation, 404 while off, token scope
  including tunnel refusal, values never in list responses, `run` injection by env and
  scrub of stdout/stderr, `reveal` policy matrix, approval round trip, audit rows carry no
  values, composer detection fixtures, scrub byte-length invariance, agent line.
  Browser suite for the view and the chip; phone 390 plus axe.

**Phase two:**
- Passphrase unlock and auto-lock; the env-key-plus-passphrase combination.
- `--header` and `--file` injection forms.
- TOTP: a `login` item may hold a seed; `pocket-vault totp <name>` returns a current code
  (the seed is never revealed; a code is a reveal of a 30-second value and is logged).
- Expiry reminders through Tasks ("Rotate the Stripe key before Nov 1").
- ultra-vault backend; import.
- MemStem ingest scrub and resolve, in the MemStem repo, using the contract above.
- Possibly a "typed by Pocket" form fill for Playwright, where the browser tool is given a
  placeholder and Pocket's side substitutes the value, so even logins stop needing a
  reveal. Depends on where the browser runs; not designed yet.

## Open questions for Brad

1. **Default policy for new items**: `use` (recommended; the agent must ask to change it)
   or `reveal` (more convenient, one tap per reveal)?
2. **Cards**: store full card numbers, or store a virtual-card number per merchant and keep
   the real card out of the box? The agent has to see a number to type it at checkout, so
   a virtual card limits what a reveal can expose.
3. **Phase one key**: is `POCKET_VAULT_KEY` in `.env` acceptable for the first release, with
   the passphrase mode following, or should the passphrase ship first even though it means
   unlocking after every restart?
4. **Agent removal**: should agents be able to remove items at all? The draft says no.
5. **Name**: "Vault" in the UI, or "Secrets"? Both appear in the wild; Vault matches
   ultra-vault and MemStem's docs.

## Non-goals

- A general password manager for people. No browser extension, no autofill on other
  devices, no sharing between users. 1Password and the like do that; the Vault is for what
  agents on this box need.
- Process isolation from the agent. See the limits above.
- A guarantee of detection. The composer check and MemStem's scrub are backstops; the
  owner storing a secret before mentioning it is the primary control.
- Sharing items across Pocket instances. Each install has its own store.
