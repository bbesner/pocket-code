# Red-team of the Pocket Code Vault design (1.39.0 plan)

Three critics attacked `docs/plans/1.39.0-vault.md` on 2026-10-12: GPT-6 Astra (correctness and security), Grok 4.6 (cost and over-engineering), and a Claude Opus subagent that checked every mechanism the design relies on against the actual code (read-only). This is a stress test of an existing design, not an independent re-derivation. Findings are merged and deduplicated, ranked by severity.

## 🔴 Critical

**1. `run` is disclosure to agent-controlled code, not "use without seeing".** (all three critics)
The daemon hands plaintext to `pocket-vault`, an agent-spawned process, which injects it into a command the agent wrote. That command can base64 the value, write it to a file, or `curl` it off the box; stdout masking catches none of that, and a parallel tool call can read `/proc/<pid>/environ`. The headline promise is true of the model's context and false of the system. Under Full access there is no approval at all.
Fix: never return values over HTTP to the agent side. The daemon decrypts and spawns the child itself (`vault.mjs` decrypt only inside the spawn path), returns scrubbed output only, and shows an approval card for every `run` even under Full access with the full command. Stronger and cheaper to reason about: owner-defined recipes per item (allowed binary, cwd, argument shape), so an agent can trigger "sync Zoho" but not arbitrary argv. Reword the claim to "the value is never in the model's context" and label `run` as execution with the credential.

**2. No authorization matrix; the loopback CLI token bypasses every policy.** (Astra, Grok)
As written the same token reaches `GET /api/vault/:id/field/:name` (plaintext), `PATCH` (policy not excluded), `put` (overwrite), `DELETE`, `rotate-key`, `init`. One `curl` with the token dumps a use-only item or flips it to `reveal-auto`. Policy enforced only on `/reveal` and in SKILL.md is a suggestion.
Fix: write the matrix down and test it over raw HTTP. CLI token: `list`, `show`, `run`, `put` create-only. Cookie only: field reads (as POST, no caching), policy changes, remove, rotate, unlock, audit. Enforce policy on every decrypt path in the daemon. Owner-only subcommands in a separate entrypoint, never on the agent's PATH binary.

**3. The reveal flow has no working mechanism in the code.** (Opus, verified against source)
- The approval inbox is a relay for native requests: `receive()` requires a `nativeId` and the current turn id, and `decide()` writes a `control_response` to Claude's stdin or a JSON-RPC reply to Codex. A synthetic `vault-reveal` row would send a bogus response to the model process and nothing would wake the CLI. Decision routes are cookie-only; the UI renders approvals in a sheet behind a banner with copy only for permissions and network kinds.
- Claude Code kills a Bash call after 2 minutes by default (max 10), so a 10-minute block dies before most phone taps; the orphaned row then suppresses the stall killer.
- The daemon cannot tell which session or turn a CLI call came from: one global bearer, session id only as text in the instruction line. Audit rows, "post the card in this conversation" and "arm the scrub for this transcript" all rest on a caller-supplied id.
Fix: per-row resolver callback for Pocket-originated rows plus a `vault-reveal` UI branch; `POST /api/vault/reveal` returning a request id and a poll route (no long-poll: undici's 300 s header timeout); `BASH_DEFAULT_TIMEOUT_MS`/`BASH_MAX_TIMEOUT_MS` in the runner env or a `reveal --wait <id>` pattern with a heartbeat TTL; `POCKET_SESSION_ID` plus a per-runner capability nonce in the runner environment (Claude runner and Codex app-server spawns), with nonce-less calls treated as owner-only reveals that go to a pending list, never armed against a transcript.

**4. The end-of-turn scrub cannot do what the design promises, and the restamp reuse is wrong.** (all three)
`restampFile` patches one fixed ASCII literal; it has no JSON-escape awareness. Transcripts store `JSON.stringify` output, so a value with quotes, backslashes or non-ASCII is not on disk in its raw form and its byte length differs. Short values (CVC, expiry, ZIP) replaced "wherever they occur" corrupt JSON numbers and break `--resume`. Turn logs carry `text_delta` chunks, so a value echoed in prose is split across lines as the normal case. There is no Codex finalize pass at all. MemStem's watcher ingests 30 s after a write, so prose echoed mid-turn is indexed before the scrub and may already be distilled. SSE replay buffers and phone clients keep the deltas. Transcript watchers, backups and `--resume` from a terminal can copy the value in the window.
Fix: drop reveal from phase one (see 7). If it ships later: a parse-aware scrubber that walks JSON string values and their escaped forms, re-serializes, and pads outside values; a minimum value length; a separate Codex rollout and turnlogs-codex pass; scrub as lines arrive, not at finalize; and the honest label: a reveal is a disclosure with a rotation path, and local cleanup is best effort.

**5. The passphrase claim is false as written.** (Astra, Grok)
"The agent would have to ask Pocket, and Pocket would ask the owner" does not hold: while unlocked, which unattended `use` requires, `/use` still decrypts on request. A passphrase protects a locked store against offline theft of the disk or a backup. The combined mode keeps unattended decryption through the env key by definition.
Fix: reword the limits section. Passphrase = protection at rest for a locked store; it is not process isolation and does not make agent access visible by itself.

**6. Cards with CVC at rest.** (Astra, Grok)
Persistent CVC storage is outside what a generic public feature should ship; three to five character fields also make output scrubbing both useless and destructive. "The agent has to see a number to type it" is a false premise: a trusted browser executor can fill a reference without the model seeing the value, which phase two already proposes.
Fix: cut `card` from phase one. If cards ever ship: virtual card per merchant, never CVC at rest, filled by Pocket's side rather than revealed.

## 🟠 Should-fix

**7. Phase one is a password manager plus a sidecar plus an approval product.** (Grok, with Astra's point that detection is not prevention)
The protection actually obtainable on this stack is "secrets stay out of prompts, transcripts, memory and backups when the agent follows the rules, with an encrypted store and a record of use". That is a store, `list`/`put`/`run`, an owner UI, an audit file, the skill and the instruction line, and the env strip. Reveal is the path that puts the secret in the provider log and then spends the rest of the design bleaching local copies, while phase two already proposes the thing that makes reveal unnecessary.
Cut from 1.39.0: reveal and the scrub; the regex-pack composer detection (keep a plain "Store in Vault" control on the composer); envelope keys and `rotate-key` on the agent binary; `card`; four policies (one bit: usable by agents, or owner-only); the two-backend interface; MemStem routes; `--header` and `--file`.

**8. `agentEnv()` is not the single gate.** (Opus, verified)
Spawns that inherit the daemon's full environment: the voice engine, thumbnail workers (headless Chrome, pdftoppm, ImageMagick on agent-written files), `git` in agent-controlled repos (a `.gitattributes` textconv or `diff.external` runs with the key), the `sh` keepers, two `execSync` calls, and `titles.mjs` defaults.
Fix: one `childEnv()` wrapper for every spawn with a test that greps for `spawn(`/`execFile(` without it, and keep `POCKET_VAULT_KEY` out of `process.env` entirely: read it from `.env` into a module variable and delete it at boot.

**9. `--header` rewriting does not work.** (Astra, Grok)
`"$POCKET_VAULT_1"` expands only through a shell, which puts the value in the child's argv (the thing being avoided); without a shell the literal string is passed and authentication fails. Drop it; if curl-shaped use is needed, the daemon builds the request from a header map.

**10. The instruction line is per process or thread, not per turn.** (Opus, verified)
Claude's `--append-system-prompt` is fixed when the long-lived runner spawns; Codex gets `developerInstructions` on thread start or resume only and skips it when `config.toml` sets `developer_instructions`; settings toggles do not restart runners. Turning the Vault on leaves live sessions without the rules. Restart idle runners on toggle, or deliver the line per turn, and warn on the Codex override.

**11. Codex Review mode.** (Opus, Grok)
The read-only sandbox blocks network, and loopback to the daemon is network; the wrapped child usually needs network too. Whether Codex's proxy permits loopback is unverified. Specify `stdio: ['ignore','pipe','pipe']`, no TTY, a test that a child's `echo $SECRET` never appears in fixture transcripts, and document that Review mode means a full escalation of the child.

**12. A declined or undecided paste persists before the user decides.** (Opus, verified)
Drafts go to `localStorage` on every input and to the outbox; a new session's first message goes to `saved-prompts.json` (in the nightly S3 copy under Object Lock for 30 days) and to the title helper model; queued messages to `followup-queue.json`; the queue editor is not covered; IME chips and dictation arrive as `input`, not `paste`. "The browser is the only point that can stop a secret reaching the provider" is also false: the server can check before dispatch, and the Vault view first is the real control.
Fix: `preventDefault` and hold the paste in memory until the chip is answered; run detection on `input`; skip recent and title for flagged messages; add a server-side pre-dispatch check.

**13. The backup does not include `vault.json`, and there is no key escrow.** (Opus, verified; Astra on rotation)
The backup script uses an explicit allowlist and lives outside the repo. `rotate-key` printing the new key puts it into the channels the feature avoids; rewrapping the live store strands older backups. Add `vault.json` and `vault-audit.jsonl` to the list; document key escrow offline; make rotation owner-only with a versioned, recoverable procedure; give generic installs a backup story.

**14. Crypto construction.** (Astra wants it specified; Grok wants it simpler)
Per-item keys with AAD = item id allow swapping fields within an item; policy and metadata are unauthenticated, so an agent with file access can edit `reveal-auto` on disk; IV generation, tag length and fail-closed behavior are unspecified. Recommendation: encrypt the whole store as one AES-256-GCM blob under one key, policy inside the blob, fresh 12-byte IV per write, fail closed on tag mismatch, decrypt into memory at boot. Simpler, hides the vendor list from backups, and removes the on-disk policy edit.

**15. Secrecy is not authorization.** (Astra)
A prompt-injected agent can misuse a perfectly hidden credential to refund, buy or change an account. `use` names no destination, operation or limit, and the card shows a script name, not what it does. Recipe-bound items (see 1) and showing the actual destination on the card are the answer; treat the agent's reason as untrusted text.

**16. Approvals need binding and lifecycle rules.** (Astra, Opus)
Single-use request ids bound to session, turn, immutable item id, field set and revision; atomic consumption; recheck policy before release; invalidate on timeout, cancel, lock or item change; explicit error when the inbox's 20-row cap refuses a request.

**17. Audit guarantees are overstated.** (Astra, Grok)
"Every use is logged" covers credential release, not downstream use; a `0600` file is writable by its owner; session attribution needs the nonce from 3; full-disk must fail closed. Call it a record of releases, best effort unless integrity lives outside agent control; sanitize reasons, which can carry secrets.

**18. ultra-vault mapping and placeholder grammar.** (Opus, verified)
ultra-vault's `kind` is an enforced enum (`api_key`, `password`, `oauth_token`, `webhook_url`, `other`; the README's "free-form" is wrong), `notes` is capped at 500 characters, `value` is one string, and there are no audit or last-used fields. MemStem's placeholder is `{{vault:slug/key}}`, which the design's name grammar cannot produce. Defer the backend; align the grammar in both documents.

**19. Browser and tunnel boundaries.** (Astra, Grok)
Require `no-store` on all Vault responses, exclude them from the service worker, keep values out of persistent browser state, validate origin for CSRF, render notes and reasons safely (a same-origin XSS becomes a vault dump), use POST for field reads, require recent authentication for sensitive actions, and state that TLS terminates at the tunnel.

**20. Temp files and `--file`.** (Astra)
A `0600` file is readable by the same user; writing `.env.local` can overwrite a real file or follow a symlink; cleanup cannot run after a crash; "shredded" cannot promise erasure on SSD or snapshots. Drop from phase one.

**21. Concurrency on `vault.json`.** (Astra, Grok)
Atomic rename does not prevent lost updates between a UI save, a `put` and a `lastUsedAt` bump. One mutex, revision checks, and crash-recovery tests.

**22. Plaintext `url` and `notes`.** (Astra, Grok)
URLs carry signed queries and tokens; notes returned to the CLI token are an unencrypted channel. Encrypt both, or keep them owner-only.

## 🟡 Minor

- Reveal under Review mode costs two taps (Bash approval, then the vault card); allowlist the read-only `pocket-vault` commands.
- The server's `.env` loader does not strip quotes while the CLI's does; a quoted key decodes differently in the two. `rotate-key` needs a daemon restart.
- A fourth skill needs the `SKILLS` and `BIN` entries, the commands block, a `commands.vault` entry, the sync trigger, `/api/me` and the skills test; an existing unmanaged `pocket-vault` folder is skipped.
- Away digests include the last tool's command text; a literal secret in a Bash command reaches the helper model regardless of the Vault.
- `run` output scrubbing needs a sliding window across chunk boundaries and the base64 and URL-encoded forms; it reduces accidental exposure and cannot constrain malicious code.
- Multi-field items need explicit field references (`--env USER=vendor-portal.username`); define rename and name-reuse behavior.
- "Approval card in the conversation" is inaccurate; approvals render in a sheet behind a banner.
- "Protects: silent use" is wording, not protection; Full-access `use` is silent until someone opens History.
- TOTP codes, import shredding and the `SecretBackend` interface are premature for a public repo whose phase one is the built-in store.

## What held up

Verified against the code: the loopback token's tunnel refusal and the 127.0.0.1 bind; the token is a single bearer, mode 0600, rotated per boot; the approval audit is append-only with fsync; MemStem's Claude Code, Codex and OpenClaw adapters reduce tool I/O to markers; Pocket's own transcript parsing drops tool-result content and the digests carry tool name plus a clipped command; the composer paste event is interceptable; `agentEnv` covers Claude turns, helper models, login, the reminder hook and the Codex app-server; the backup excludes `.env` and `cli-token`; ultra-vault never lists values; MemStem's vault layer is designed and unbuilt; the atomic-write, trash and exit-3 patterns exist.

Unverifiable without running it: whether Codex's sandbox permits loopback; whether MemStem's re-ingest of a scrubbed transcript replaces distillations already derived; whether a tenant MemStem in Docker can reach the host's loopback Pocket.

## Where the critics disagreed

Astra would specify the envelope construction rigorously; Grok would delete it and encrypt the whole store. Both close the same holes; the whole-store form is less code and also hides metadata from backups, so it is the recommendation above. Astra treats the composer check as worth keeping with a server-side pre-dispatch check added; Grok would defer the regex pack entirely. Keeping a plain "Store in Vault" composer control and deferring the detection pack satisfies both.

## The single most important change

Stop returning plaintext to the agent's process. The daemon runs the command itself, shows an approval for every run, and binds items to owner-defined recipes where possible. With that in place, phase one shrinks to the encrypted store, the owner UI, `list`/`put`/`run`, the audit file, the skill and instruction line, and the env strip. Reveal, scrub, cards, composer detection, envelope keys and the backend interface wait for phase two, and the limits section stops promising what the OS-user boundary cannot deliver.
