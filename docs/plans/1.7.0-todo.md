## A. Checks that decide the design
- [x] 1. Do `TaskCreated` / `TaskCompleted` hooks fire for background shell jobs?
      No (CLI 2.1.281). The stream reports them instead: `system/background_tasks_changed`
      (full task list), `task_started`, `task_updated`, `task_notification`.
- [x] 2. A persistent stream-json process: is the `result` event a reliable turn
      boundary, and do background-job notices still arrive after the turn ends?
      Yes. With stdin left open, a finished background job makes the CLI start a new
      turn by itself (`system/init` ... `result`) with no user message; a later user
      message gets its own `result`; closing stdin exits 0. Pocket must therefore
      accept turns that begin without a message.

## B. Persistent sessions
- [x] 3. One live Claude Code process per session; each message goes to its stdin;
      turn end comes from the `result` event, not process exit.
- [x] 4. Keep surviving Pocket restarts (stdin via a named pipe that a restarted
      server can reattach to).
- [x] 5. One live process per session: refuse to start a second one while another
      process (code-server, terminal) is driving the same session.
      Done via the transcript (code-server keeps no session id on its command line):
      409 if another app wrote a user/assistant line in the last 45s; a live process is
      replaced if another app added turns since Pocket's last one (fork guard, sizes
      persisted in owned-transcripts.json).

## C. Idle close and stall watchdog
- [x] 6. 60-minute idle close. The clock runs only with no turn, no background job,
      and nothing waiting on Brad.
- [x] 7. Questions/approvals waiting on Brad are exempt from the idle close.
- [x] 8. Replace the 2-hour `TURN_KILL_MS` with a stall watchdog: kill only after
      30 minutes with no stream/hook activity, no running background job and no
      CPU use under the process (connector processes excluded).
      Questions/approvals only exist inside a turn, so the idle clock never runs while
      one waits; the stall watchdog skips turns with one pending.

## D. Codex parity
- [x] 9. Confirm Codex turns have no wall-clock cap; apply the same idle/stall
      rules where Codex's app-server model allows it.
      Codex has no wall-clock cap (only 60s RPC timeouts). It stays one app-server per
      turn: a long-lived connection would hold the per-thread writer lock and block
      code-server for up to an hour. Its existing 423 lock check already refuses sends
      while another app owns the thread.
